## requirements.md

```markdown
# 需求规格说明书

> 状态：草稿

## 背景

## 目标

## 功能需求

### R-01: ...

当...
系统应当...

### R-02: ...

## 非功能需求

### NFR-01: ...

## 验收标准 / 人工确认点

### AC-01

Given ...
When ...
Then ...

## 范围外

## 待确认问题

### 阻塞性问题

- Q-01: ...（为什么需要确认：...；影响：...）

### 非阻塞假设

- A-01: ...（后续可调整点：...）
```

要求：

- 需求使用 `R-xx` 编号。
- 能用 EARS 表达时，优先使用"当...系统应当..."。
- 非功能需求只写和本功能强相关的内容。
- 待确认问题会阻塞设计或实现时，必须放在回复最后的“需确认后再继续”部分，先问用户，不提示进入下一阶段。
- 没有待确认问题时，在“待确认问题”中写“无”。
- 轻微假设不阻塞下一阶段时，写入“非阻塞假设”，并说明后续可调整点。

要求：

- 说明采用方案和选择原因。
- 保持设计贴合现有代码结构。
- 风险只保留会影响实现或人工验证的关键项。
- 新增公共函数、工具类、Hook、组件、服务封装或跨模块能力前，必须记录检索范围和结论。
- 如果现有公共能力不满足需求，必须说明缺少什么、如何改进、影响哪些调用方，以及本次为何复用、扩展或新建。
- 仅在复用、降低复杂度或符合既有模式时抽象封装；单次使用的简单判断优先写在使用位置。
- 注释策略只要求解释业务意图、边界条件、关键判断或非显而易见的实现原因。
- 设计中存在会影响任务拆解、实现范围、公共能力处理或验证方式的问题时，必须列入“阻塞性问题”，并在回复最后要求用户先确认。

## tasks.md

```markdown
# 任务拆解

> 状态：草稿

- [ ] task-01: [API] 增加短信验证码接口封装
- [ ] task-02: [UI] 增加短信验证码表单
- [ ] task-03: [State] 增加验证码倒计时状态

## task-01: [API] 增加短信验证码接口封装

**追踪需求：** R-01, R-02
**依赖任务：** 无
**修改范围：** src/api/login.ts
**公共能力处理：** 复用现有请求封装；检索 src/api、src/utils/request 等目录，未发现需要新增公共能力
**代码注释要求：** 按实现约束补充必要注释；接口路径或参数映射存在业务特殊性时说明原因
**完成标准：**
- 新增发送验证码方法
- 新增验证码登录方法
- 复用现有请求封装和错误处理
- 不为单次使用的简单判断新增工具函数

**自动化验证：**
- 测试目标：验证发送验证码和验证码登录接口的参数映射、成功返回和错误处理。
- 测试用例 / 脚本：新增或补充 `src/api/login.spec.ts`，mock 请求封装，断言接口路径、请求方法、参数和异常透传。
- 执行命令：按项目测试框架填写，例如 `npm run test -- login.spec.ts`。
- 兜底检查：如需执行 `npm run lint` / `npm run build`，需标注“仅验证基础静态检查 / 构建，不证明接口逻辑正确”。

**人工验证关注点：**
- 本任务为 API 封装，无单独 UI 人工验证；真实接口参数可在联调任务中验证。
- UI 任务需写明入口、步骤、预期展示、错误提示、加载态、禁用态和兼容性关注点。

**待确认问题：** 无
```

要求：

- 单个任务保持小粒度，预计 30 分钟内能完成。
- 任务应可独立回滚。
- 依赖只能指向编号更小的任务，禁止循环依赖；无依赖时写"无"。
- 自动化验证优先覆盖新增或修改逻辑，写清测试目标、测试用例 / 脚本、执行命令和覆盖点。
- 不要默认只写 `npm run lint`、`npm run build`、类型检查或编译；这些只能作为基础兜底，不能证明新增逻辑正确。
- 确实没有合适的自动化方案时，说明原因，并补充可执行的人工验证步骤；兜底命令需标注局限。
- 公共能力处理必须写明复用、扩展、新建或不涉及；涉及公共能力时写明检索范围和结论。
- 代码注释要求必须说明关键逻辑是否需要注释；避免复述代码行为的空泛注释。
- 任务完成标准应体现克制封装要求，避免为单次使用的简单逻辑新增抽象。
- 完成一个任务后更新勾选状态。
- 人工验证关注点写在对应任务下，不默认创建独立测试报告。
- UI 任务可以人工验证为主，必须写明页面入口、操作步骤、预期效果和异常状态；如项目已有组件测试能力，再补充对应测试。
- 任务中存在会影响执行顺序、修改范围、公共能力处理或验证命令的问题时，必须列入“待确认问题”，并在回复最后要求用户先确认。

## 阻塞性待确认问题回复格式

```text
需确认后再继续

1. {问题}
   为什么需要确认：{原因}
   影响：{不同选择对需求 / 设计 / 任务 / 实现 / 验证的影响}

请先明确以上问题；确认后我再进入 {下一阶段名称}。
```

要求：

- 只要存在阻塞性问题，回复最后必须使用该格式或等价的清晰格式。
- 存在阻塞性问题时，不要同时提示“回复 Approve 或 Proceed 进入下一阶段”。
