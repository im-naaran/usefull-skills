# 规范驱动开发编排器

## 核心流程

按以下顺序推进功能开发：

```text
需求 -> 设计 -> 任务 -> 执行
```

在需求、设计和任务拆解获得用户确认前，禁止修改生产代码。实现必须能追溯到对应需求和任务。

---

## 启动规则

当用户消息以以下关键词开头时，启动流程：

```text
新功能
开发功能
需求开发
Start Feature
New Feature
```

创建规格目录：

```text
specs/{YYYYMMDD_feature_name}/
├── project-context.md
├── requirements.md
├── design.md
├── tasks.md
└── changelog.md
```

`YYYYMMDD` 使用当前日期，`feature_name` 从用户需求提炼为小写下划线名称。

启动后输出：

```text
规范驱动开发编排器已启动

Feature: {feature_name}
Spec 目录: specs/{YYYYMMDD_feature_name}/

正在进入 Phase 0: 项目上下文分析...
```

---

## 生产代码保护

Phase 0 到 Phase 3 期间只允许修改 `specs/{YYYYMMDD_feature_name}/` 下的规格文档，禁止修改生产代码。生产代码指项目实际的源码与工程文件，需结合 Phase 0 识别的项目结构判断，常见示例：

```text
src/、app/、lib/（前端 / 通用源码）
include/、core/、firmware/（C/C++、嵌入式源码）
server/、internal/（后端服务源码）
```

除非用户明确批准，禁止升级依赖、修改锁文件、调整 CI/CD、Docker、部署或基础设施配置。

---

## Phase 0: 项目上下文

阅读项目结构与已有规范，生成 `project-context.md`。优先查看：

```text
README.md
依赖与构建配置（package.json、Cargo.toml、CMakeLists.txt、pom.xml、go.mod 等）
docs/
specs/
architecture/
```

记录技术栈、架构模式、关键约束、相关模块和已知风险。

完成后展示 `project-context.md` 并自动进入 Phase 1：

```text
Phase 0 完成，已生成项目上下文。

正在进入 Phase 1: 需求...
```

---

## Phase 1: 需求

生成 `requirements.md`，包含：

- 背景与目标
- 功能需求，使用 `R-01`、`R-02` 编号
- 必要的非功能需求
- 验收标准或人工确认点
- 明确的范围外内容

展示文档后等待用户确认：

```text
Phase 1 完成。

请确认需求规格说明书。

回复 Approve 或 Proceed 进入下一阶段。
```

---

## Phase 2: 设计

用户确认需求后，生成 `design.md`，包含：

- 采用方案和选择原因
- 涉及模块与数据流
- 接口、类型或状态设计
- 主要风险与规避方式

展示文档后等待用户确认：

```text
Phase 2 完成。

请确认技术设计文档。

回复 Approve 或 Proceed 进入下一阶段。
```

---

## Phase 3: 任务

用户确认设计后，生成 `tasks.md`。任务必须足够小，能独立实现、验证和回滚。

任务清单格式：

```text
- [ ] task-01: [模块] 任务描述
```

每个任务应标注：

- 追踪需求
- 依赖任务（无依赖写"无"，依赖只能指向编号更小的任务，禁止循环依赖）
- 修改范围
- 完成标准
- 自动化验证（按项目实际可执行的编译、构建、烧录、测试或检查命令；无法自动验证时写"无"）
- 人工验证关注点（需要人工验收时的关注点）

展示文档后等待用户确认：

```text
Phase 3 完成。

请确认任务拆解。

回复 Approve 或 Proceed 进入下一阶段。
```

---

## Phase 4: 执行

按 `tasks.md` 的依赖关系执行，优先选取依赖已全部完成的任务。依赖互不冲突的任务可并行执行，存在依赖关系的任务必须等待前置任务完成。仅当多个任务的修改范围不重叠时才并行，修改范围有交叉的任务串行处理以避免冲突：

1. 选取依赖已满足且未完成的任务，读取任务和对应需求、设计。
2. 实现最小代码变更。
3. 执行任务标注的自动化验证。
4. 更新任务状态，并在 `changelog.md` 追加一条记录。
5. 在任务下补充人工验证关注点。
6. 向用户汇报本轮完成的任务、校验结果和下一步；并行完成多个任务时一并汇报。

不得声明"测试通过"、"验证通过"或"生产可用"，除非用户明确确认人工验证结果。

---

## 变更处理

实现阶段如果出现新需求、设计缺陷或任务拆分不合理，先停止编码，回到对应阶段更新 `requirements.md`、`design.md` 或 `tasks.md`，获得用户确认后再继续。

---

## 状态与续传

每个规格文档头部带状态行：

```text
> 状态：草稿
```

- 文档生成时状态为"草稿"。
- `project-context.md` 生成后直接标记为"已确认"。
- `requirements.md`、`design.md`、`tasks.md` 在用户 Approve 对应阶段后更新为"已确认"。

当用户要求继续已有功能（如"继续 {feature_name}"）时，按以下规则恢复进度：

1. 依次检查 `project-context.md` -> `requirements.md` -> `design.md` -> `tasks.md`。
2. 定位第一个不存在或状态为"草稿"的文档，从其对应 Phase 续接。
3. 四个文档均为"已确认"时进入 Phase 4，按 `tasks.md` 勾选状态继续未完成任务。
4. 续接前先向用户简述当前阶段与下一步，确认后再继续。

---

## 变更记录

`changelog.md` 只记录历史流水，按时间顺序追加，不覆盖既有内容。记录时机：

- 每个阶段产物获得确认（Phase 1/2/3 Approve）时追加一条。
- Phase 4 每完成一个任务时追加一条。
- 需求或设计发生变更时，记录变更原因与影响范围。

---

## 异常与边界处理

- **spec 目录已存在**：先询问用户是续传（按「状态与续传」恢复）还是新建（更换 feature_name 或确认覆盖）。
- **需求过于模糊**：无法提炼 feature_name 或核心目标时，先追问澄清，不要臆测生成。
- **用户要求跳过阶段直接编码**：说明跳过需求、设计或任务的风险，获得用户明确确认后才可跳过，并在 `changelog.md` 记录该决定。
- **无法写入 `specs/`**：提示用户检查目录权限或改用其他路径，暂停流程。

---

## 产物自检清单

生成各阶段产物后自检：

- **需求**：每条需求可测；有验收标准或人工确认点；范围外已明确。
- **设计**：需求追踪表覆盖全部需求，无空缺；方案贴合现有代码结构。
- **任务**：每个任务可独立回滚；依赖关系无环；均标注验证方式。
