# 规范驱动开发编排器

## 核心流程

按以下顺序推进功能开发：

```text
需求 -> 设计 -> 任务 -> 执行
```

在需求、设计和任务拆解获得用户确认前，禁止修改生产代码。实现必须能追溯到对应需求和任务。

---

## 启动规则

当用户消息以以下关键词开头时，启动流程：

```text
新功能
开发功能
需求开发
Start Feature
New Feature
```

创建规格目录：

```text
specs/{YYYYMMDD_feature_name}/
├── project-context.md
├── requirements.md
├── design.md
├── tasks.md
└── changelog.md
```

`YYYYMMDD` 使用当前日期，`feature_name` 从用户需求提炼为小写下划线名称。

启动后输出：

```text
规范驱动开发编排器已启动

Feature: {feature_name}
Spec 目录: specs/{YYYYMMDD_feature_name}/

正在进入 Phase 0: 项目上下文分析...
```

---

## 生产代码保护

Phase 0 到 Phase 3 期间只允许修改 `specs/{YYYYMMDD_feature_name}/` 下的规格文档，禁止修改生产代码。生产代码指项目实际的源码与工程文件，需结合 Phase 0 识别的项目结构判断，常见示例：

```text
src/、app/、lib/（前端 / 通用源码）
include/、core/、firmware/（C/C++、嵌入式源码）
server/、internal/（后端服务源码）
```

除非用户明确批准，禁止升级依赖、修改锁文件、调整 CI/CD、Docker、部署或基础设施配置。

---

## 通用规则

- **确认优先**：阶段产物中如有影响下一步的需求边界、设计方向、任务拆解、公共能力、实现范围或验证方式的问题，必须在回复最后以“需确认后再继续”列出，说明原因和影响；用户确认前不得进入下一阶段。非阻塞假设写入文档即可。
- **实现克制**：新增或修改代码需补充必要注释，解释业务意图、关键判断或边界条件；禁止空泛注释。仅在复用、降低复杂度或符合既有模式时抽象封装，单次使用的简单逻辑优先写在使用位置。
- **公共能力复用**：新增公共函数、工具、Hook、组件或服务前，先检索项目已有实现；已有能力不满足时，在设计或任务中说明缺少什么、如何改进、影响范围，以及本次选择复用、扩展或新建的原因。
- **验证有效性**：任务验证应优先覆盖新增逻辑，编写或补充单元测试、接口测试、组件测试、脚本化验证或最小复现脚本。UI 改动以人工验证为主，写清入口、步骤、预期效果和异常状态。`lint` / `build` / 类型检查只能作为基础兜底，除非没有更合适方案，不得作为唯一验证。

## Phase 0: 项目上下文

阅读项目结构与已有规范，生成 `project-context.md`。优先查看：

```text
README.md
依赖与构建配置（package.json、Cargo.toml、CMakeLists.txt、pom.xml、go.mod 等）
docs/
specs/
architecture/
```

记录技术栈、架构模式、关键约束、相关模块、现有公共能力与复用点、已知风险。

完成后展示 `project-context.md` 并自动进入 Phase 1：

```text
Phase 0 完成，已生成项目上下文。

正在进入 Phase 1: 需求...
```

---

## Phase 1: 需求

生成 `requirements.md`，包含：

- 背景与目标
- 功能需求，使用 `R-01`、`R-02` 编号
- 必要的非功能需求
- 验收标准或人工确认点
- 明确的范围外内容
- 待确认问题：列出会阻塞设计或实现的问题；没有则写“无”

展示文档后按“确认优先”规则处理；无阻塞问题时等待用户确认：

```text
Phase 1 完成。

请确认需求规格说明书。

回复 Approve 或 Proceed 进入下一阶段。
```

---

## Phase 2: 设计

用户确认需求后，生成 `design.md`，包含：

- 采用方案和选择原因
- 涉及模块与数据流
- 接口、类型或状态设计
- 公共能力复用评估：检索范围、可复用能力、差距和处理决策
- 实现约束：注释策略、封装边界、最小影响面
- 主要风险与规避方式
- 待确认问题：列出会阻塞任务拆解或实现的问题；没有则写“无”

展示文档后按“确认优先”规则处理；无阻塞问题时等待用户确认：

```text
Phase 2 完成。

请确认技术设计文档。

回复 Approve 或 Proceed 进入下一阶段。
```

---

## Phase 3: 任务

用户确认设计后，生成 `tasks.md`。任务必须足够小，能独立实现、验证和回滚。

任务清单格式：

```text
- [ ] task-01: [模块] 任务描述
```

每个任务应标注：

- 追踪需求
- 依赖任务（无依赖写"无"，依赖只能指向编号更小的任务，禁止循环依赖）
- 修改范围
- 公共能力处理（复用 / 扩展 / 新建 / 不涉及；涉及公共能力时写明检索结论）
- 代码注释要求（说明哪些关键逻辑需要注释；无特殊要求时写"按实现约束补充必要注释"）
- 完成标准
- 自动化验证（优先写能验证新增逻辑的测试或脚本；没有更好方案时才写 lint/build 等兜底命令，并说明局限）
- 人工验证关注点（UI 场景必须写明入口、步骤、预期效果和异常状态）
- 待确认问题（列出会阻塞执行的问题；没有则写“无”）

展示文档后按“确认优先”规则处理；无阻塞问题时等待用户确认：

```text
Phase 3 完成。

请确认任务拆解。

回复 Approve 或 Proceed 进入下一阶段。
```

---

## Phase 4: 执行

按 `tasks.md` 的依赖关系执行，优先选取依赖已全部完成的任务。依赖互不冲突的任务可并行执行，存在依赖关系的任务必须等待前置任务完成。仅当多个任务的修改范围不重叠时才并行，修改范围有交叉的任务串行处理以避免冲突：

1. 选取依赖已满足且未完成的任务，读取任务和对应需求、设计。
2. 按任务中的公共能力处理结论再次核对相关实现；发现遗漏或差距变化时，停止编码并回到设计或任务阶段更新说明。
3. 实现最小代码变更，补充必要注释，避免为单次使用的简单逻辑新增抽象。
4. 执行任务标注的验证；优先执行能验证新增逻辑的测试或脚本，UI 按任务说明人工验证，`lint` / `build` 只作基础兜底。
5. 更新任务状态，并在 `changelog.md` 追加一条记录。
6. 在任务下补充人工验证关注点。
7. 向用户汇报本轮完成的任务、校验结果和下一步；并行完成多个任务时一并汇报。

不得声明"测试通过"、"验证通过"或"生产可用"，除非用户明确确认人工验证结果。

---

## 变更处理

实现阶段如果出现新需求、设计缺陷或任务拆分不合理，先停止编码，回到对应阶段更新 `requirements.md`、`design.md` 或 `tasks.md`，获得用户确认后再继续。

---

## 状态与续传

每个规格文档头部带状态行：

```text
> 状态：草稿
```

- 文档生成时状态为"草稿"。
- `project-context.md` 生成后直接标记为"已确认"。
- `requirements.md`、`design.md`、`tasks.md` 在用户 Approve 对应阶段后更新为"已确认"。

当用户要求继续已有功能（如"继续 {feature_name}"）时，按以下规则恢复进度：

1. 依次检查 `project-context.md` -> `requirements.md` -> `design.md` -> `tasks.md`。
2. 定位第一个不存在或状态为"草稿"的文档，从其对应 Phase 续接。
3. 四个文档均为"已确认"时进入 Phase 4，按 `tasks.md` 勾选状态继续未完成任务。
4. 续接前先向用户简述当前阶段与下一步，确认后再继续。

---

## 变更记录

`changelog.md` 只记录历史流水，按时间顺序追加，不覆盖既有内容。记录时机：

- 每个阶段产物获得确认（Phase 1/2/3 Approve）时追加一条。
- Phase 4 每完成一个任务时追加一条。
- 需求或设计发生变更时，记录变更原因与影响范围。

---

## 异常与边界处理

- **spec 目录已存在**：先询问用户是续传（按「状态与续传」恢复）还是新建（更换 feature_name 或确认覆盖）。
- **需求过于模糊**：无法提炼 feature_name 或核心目标时，先追问澄清，不要臆测生成；问题放在回复最后的“需确认后再继续”部分。
- **用户要求跳过阶段直接编码**：说明跳过需求、设计或任务的风险，获得用户明确确认后才可跳过，并在 `changelog.md` 记录该决定。
- **无法写入 `specs/`**：提示用户检查目录权限或改用其他路径，暂停流程。

---

## 产物自检清单

生成各阶段产物后自检：

- **需求**：每条需求可测；有验收标准或人工确认点；范围外已明确；阻塞性问题已暂停推进并放在回复最后。
- **设计**：需求追踪覆盖全部需求；方案贴合现有结构；公共能力检索、差距和决策已说明；阻塞性问题已暂停推进并放在回复最后。
- **任务**：任务可独立回滚；依赖无环；标注公共能力处理、注释要求和验证方式；验证覆盖新增逻辑，未默认只用 lint/build；阻塞性问题已暂停执行并放在回复最后。
- **执行**：注释解释关键意图；未过度封装；公共能力复用或差距说明完整；已执行逻辑测试 / 脚本 / UI 人工验证，或说明无法验证的原因和兜底命令局限。
